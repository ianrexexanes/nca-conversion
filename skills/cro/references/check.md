# The /cro check procedure

This is the procedure `/cro check` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as the deck's file name, goes in quotation marks. Work through the gates in order. The output is one report with one row for each gate.

A gate that did not run is SKIPPED with its reason, never PASS. A FAIL is fixed in the page, and the checker, the deck and the lists a checker reads are left as they are to reach green. A changed word goes back through `/cro page`, because the deck is the copy's one source.

1. Copy gate. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/deck_check.py "<deck>" --final`. If it fails, stop, send the user back to `/cro page`, and check nothing else. Then write the built page's text to a folder by running the site command of step 2 with `--visible-text "<text folder>"`; that one run is the site gate too. A text folder that cannot be written stops the run with exit 2 before any row is worked out. Each file starts with the title on line 1 and the meta description on line 2, an empty line when the page has none, then the page text. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/client_check.py "<text folder>/<page>.txt"` over each file in the folder and fix every FAIL, with one exception: a FAIL on words the page means to say, such as the name of an AI product on a page that sells an AI service or a score the owner publishes, is put to the user, and on their yes the line stays and the gate's row gives the reason. A WARN is read and either fixed or kept for a stated reason. The text includes the navigation and the footer, because a reader sees both.
2. Site gate. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/site_check.py --dist "<dist folder>" --deck "<deck>" --map "<page URL>=<namespace>" --pages "<pages.json>" --forbid "<words file>" --visible-text "<text folder>"`. For live pages give `--url <address>...` in place of `--dist`; then `SITEMAP` and `ROBOTS` are SKIPPED, because a live site's files are not read. A page's URL is its path from the dist folder, such as `/index.html`. `--map` names the namespace each page shows; a deck with variants needs the page's letter after the namespace, such as `--map /b.html=p.b`, and a page with no `--map` line is SKIPPED for `PARITY` and `FAQ_SCHEMA`. `--pages` is a JSON list of `{"url": address, "mode": "search" or "direct", "paid": true or false, "keyword": text or null}`, one entry for each page. `--forbid` is the user's own list of words the site must never show, one for each line; ask for it and leave the option out when there is none. `PLACEHOLDER` and `FORBIDDEN` read the title, the meta description and the page text, and the row says which of the three held the word. The rules are `H1`, `TITLE`, `META_DESCRIPTION`, `CANONICAL`, `ALT`, `PLACEHOLDER`, `FORBIDDEN`, `PARITY`, `FAQ_SCHEMA`, `NOINDEX`, `LINK`, `SITEMAP` and `ROBOTS`. With `--dist`, the error page (`404.html`) and Google's verification file are not launch pages: each is a `SKIPPED` row, unless the pages list names it. `NOINDEX` is a WARN that carries the word UNVERIFIED, for this reason: Google states that a noindexed page is dropped from Search results (https://developers.google.com/search/docs/crawling-indexing/block-indexing), and that AdsBot, the crawler that checks ad destinations, follows its own robots.txt group (https://developers.google.com/search/docs/crawling-indexing/google-special-case-crawlers). Google Ads requires an ad destination to be crawlable by AdsBot (https://support.google.com/adspolicy/answer/6368661) and uses what its crawlers find to judge ad quality (https://support.google.com/google-ads/answer/2404197). None of the four says whether a noindexed page stays usable as an ad destination, so the rule that a paid Direct page carries noindex only when a Search page owns the keyword is the plugin's, and it is read as a warning until Google's pages say it outright. Report every WARN to the user with that line. The `LINK` check on a live run asks every same-origin link once for its status and reads no body, so a page with many links takes longer.
3. Image text. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/asset_text_check.py --dir "<images folder>" --forbid "<words file>"`. It reads the text each image carries in its metadata, never its pixels, and fails a placeholder word (`ASSET_TEXT`) or a word from the user's own list (`FORBIDDEN`). Use the same words file as step 2, or leave `--forbid` out when there is none. A folder with no images is SKIPPED.
4. Redirects. Ask the user which addresses must redirect and where, write them to a cases file, and run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/redirect_check.py --cases "<cases.json>"`. Each case is `{"from": address, "to": address, "status": number, "hops": [numbers]}`. `status` is the status of the final answer at `to` (200 for a page that loads), not the redirect's own code: `{"from": "http://example.com/", "to": "https://example.com/", "status": 200}`. `hops` is left out unless a hop other than a permanent redirect is meant. The script fetches each hop with an ordinary Chrome agent, and it fails a wrong target, a wrong status, a chain that runs past the redirect limit, and an end that is not HTTPS. With no redirects to check, this gate is SKIPPED.
5. Launch render. Run `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/launch_render.py <address>... --out "<folder>"`, which reads each built page at 375, 390, 820 and 1440 pixels wide (`--widths` takes another comma list). Each address is checked first: it starts with `http://`, `https://` or `file://`, and a bad one stops the run with exit 2 before a browser opens. Pass `--deck "<deck>"` for every page built from `/cro page`, and `--variant` when that deck has variants, so the button label is checked against the first screen and one target. When the pages have different decks, run it once per page, because one run checks every address against one label. Add `--action-color` with the `colors.action` value of `_design/tokens.json` when the project has that file, and `--landing` for a page built without a menu on purpose. A FAIL is fixed in the page. Two kinds are confirmed in an ordinary browser first: a `PAGE_ERROR`, because this run blocks tag hosts and every non-GET request, which can itself make a page script fail, and a `CONTRAST` FAIL, because the pass reads a background from the element's own ancestors and misses one drawn by a sibling layer. A WARN is fixed, or kept with a stated reason.
6. Search check, for each page the pages list marks as `search`: `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/search_check.py "<address or saved file>" --keyword "<keyword>"`, with `--variant` for each plural or closed form the page uses. For a saved file add `--url "<the page's live address>"`, or the URL placement reads NOT CHECKED, which leaves that placement SKIPPED in the row. It reports placements and never fails a page by itself, but a MISSING placement is a FAIL in the row and heading counts never fail it. A Direct page is SKIPPED for this gate, because a Direct page has no keyword placement.
7. Speed. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/speed_check.py "<address>" --strategy both` for each live address. A page that is not live yet is SKIPPED; say what was and was not measured.
8. Form. Run `/nca-conversion:cro form` for the page's form, and take its result as this gate's row. That command follows its own procedure, including what it never sends without the owner's yes.
9. Motion review, optional. When Emil Kowalski's skills are installed, offer to run them over the built page's code as a review of its motion against the design principle in `${CLAUDE_PLUGIN_ROOT}/skills/design-handoff/references/design-rules.md`: motion only where it has a job. It is the user's choice, it changes nothing by itself, and it is left out of the report's gate rows. When they are not installed, say they were skipped.
10. Report. Write one row for each gate in a table with the columns Gate, Result and Why, with the result PASS, FAIL or SKIPPED, and the reason for every SKIPPED and FAIL. Under the table, list the fixes still open, the `NOINDEX` warnings with their UNVERIFIED line, and what the checks cannot see: text that scripts draw after the page loads, a noindex sent as an `X-Robots-Tag` header, anything behind a consent banner, and the launch render's text on images or gradients, which it lists as not measured. Offer the next step: fix the FAILs, then run the check again.
