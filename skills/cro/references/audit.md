# The /cro audit procedure

This is the procedure `/cro audit <url> [mode] [keyword] [traffic] [page role] [register]` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as a project folder or a report's file name, goes in double quotes after the script path. Work through the steps in order.

1. Mode, traffic source, page role and register come from the arguments; ask once, in one message, for whatever is missing. Ask the mode first, in one line: Search or Direct. A Search page gets its visitors from organic search for a researched keyword; a Direct page gets the visitors its owner sends (paid ads, outreach, email), and "Direct" here never means the Direct channel in GA4. The definitions are in `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/modes.md`. For a Search page also ask the keyword and its spelling variants. The plugin never picks a keyword: if the user has none, say that keyword research comes first (claude-seo's DataForSEO route when it is installed, otherwise the user's own result), then still run the audit, with step 4 reporting the page's apparent target and saying the keyword is not confirmed. For a Direct page ask for the ad, email or message that sent the visitor, or its text, because factor 2 is judged against it. Then ask where the traffic comes from: cold outreach, ads, search, mixed or unknown. Page role is homepage, service or landing; any other page is audited as the nearest of the three, and the report says so. Register is the page's archetype, for example Conservative B2B (DACH), Technical / industrial, Consumer / lifestyle, Mission / nonprofit or Direct-response. Sheet values use `search` or `direct`; `homepage`, `service` or `landing`; and `cold-outreach`, `ads`, `search`, `mixed` or `unknown`.
2. Read `${CLAUDE_PLUGIN_ROOT}/skills/conversion-page-audit/references/evidence-rules.md` before concluding anything.
3. Facts: run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/conversion-page-audit/scripts/page_facts.py <url>`. It reads the static markup only.
4. Search check, Search pages only: run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/search_check.py <url> --keyword "<keyword>" --out <dir>/search.json --json` with the page's keyword, adding `--variant "<variant>"` once per spelling variant, where `<dir>` is the audit data folder and the result is its `search.json`. It reads the six placements, the heading counts and the body uses, and it sits outside the score: a missed placement is a finding in the report and a leak in the client version, never points off a factor, and the check never fails a page on how many headings carry the keyword. Without a confirmed keyword run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/search_check.py <url> --out <dir>/search.json --json` instead, with no `--keyword` and no `--variant`: it reports the page's apparent target, marks the keyword as not confirmed, and counts no placement as a miss. On a Direct page this step is skipped and no `search.json` is written. When the script exits 3 the page could not be read: put the check under Could not check with the script's reason and go on with what you have.
5. Rendered capture: run `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/render_check.py <url> --out <dir>`, with `<dir>` being `render/` inside the audit data folder. Rendered evidence comes only from `render_check.py`, the one route that blocks analytics. If `${CLAUDE_PLUGIN_DATA}/venv/bin/python` does not exist, every rendered-only check goes to Could not check with the reason and "run `/cro setup`". No form is sent and nothing is clicked. The script exits 3 when anything is missing, so read `render.json`: every viewport present under `viewports` is usable, and `could_not_check` holds the reason for what is missing (the page did not load, an HTTP error, the browser would not launch, or one view failed). Only what is missing goes to Could not check, with that reason, and the exit code alone decides nothing. Copy and facts come from `render.json` and the first-screen shots; a long page's `*-full.png` is layout evidence only, because an image viewer shrinks a very tall screenshot to a sliver.
6. Speed: run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/speed_check.py <url> --out <file>`, with `<file>` being `speed.json` in the audit data folder. The result names its source and the date it was run.
7. The first screen, on desktop and on phone, judged by the four questions in order, one score each (factors 1 to 4): What's in it for me? Is it for me? Does it work? What do I do next? When the two views differ, the lower one sets the score and the evidence says which it was. A first-screen element that looks blank or unfinished (a map, a video, a 3D viewer) goes to Could not check with that reason and is not scored low; check it in the other view first when one exists. On a Direct page, factor 2 is judged against the ad, email or message from step 1; when it was not given, factor 2 scores the audience naming alone and its evidence says so.
8. The rest of the page in the long-form audit order from `${CLAUDE_PLUGIN_ROOT}/skills/conversion-page-audit/references/audit-framework.md` (factors 5 to 9). For cold traffic, pain comes before proof; for warm search traffic, proof comes before pain.
9. Factor 10 reads only what was measured: the speed label in `speed.json` (PageSpeed Insights or lab data, with its date) together with `horizontal_scroll` for the phone in `render.json`. When the label is `could not check`, factor 10 is not checked, whatever the phone render shows, and it is never guessed from how the page looks. When the phone render did not report `horizontal_scroll` (the phone view failed or was not taken), factor 10 is judged on the measured speed alone and scores 5 at most, because the middle and high anchors need a phone view with no horizontal scroll; the evidence says the scroll was not checked, and a score that poor speed sets on its own (the low anchor) stands.
10. Missing, not applicable and not checked are three different things. A missing form, button or proof is a finding and scores low. What the page role does not need is handled by its anchors in `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/score-anchors.md`, which for factors 1 and 2 hold a line for each mode; apply the line of the page's mode. Only what could not be observed is left unscored.
11. Write the score sheet to `score.json` in the audit data folder, with the page's `mode` and `page_role` and one entry per factor holding its `evidence`, or `score` null and its reason in `not_checked`, then run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/score.py <sheet> --json`. Exit 2 means the sheet is invalid: fix the sheet from the lines it prints, which name the factor, and run it again. Never add the total by hand. This is an example of a finished sheet:

```json
{
  "page": "https://harborlane.example/services/bike-repair/",
  "mode": "search",
  "page_role": "service",
  "traffic": "search",
  "register": "Consumer / lifestyle",
  "factors": [
    {"id": 1, "score": 6, "evidence": "H1 'Bike repair in Harbor Lane' names the service and place, no result; desktop and phone alike."},
    {"id": 2, "score": 6, "evidence": "First lines speak to commuters in general terms; they match the intent behind the keyword."},
    {"id": 3, "score": 3, "evidence": "Hero is a stock photo of a smiling mechanic; no rating or logo until the third screen."},
    {"id": 4, "score": 7, "evidence": "One green button, 'Book a repair slot', top right and again under the hero."},
    {"id": 5, "score": 6, "evidence": "Three price tiers listed with what each includes; no turnaround time."},
    {"id": 6, "score": 5, "evidence": "Two named quotes at mid page; no star rating with its source."},
    {"id": 7, "score": 4, "evidence": "No answer to 'how long will it take' or 'what if it is not fixed'."},
    {"id": 8, "score": 7, "evidence": "Booking form has four fields, none optional, and says a reply comes within one working day."},
    {"id": 9, "score": 6, "evidence": "Clear order and readable type; the price table is hard to scan on a phone."},
    {"id": 10, "score": null, "not_checked": "speed.json label is 'could not check', so there is no measurement."}
  ]
}
```

12. The internal report, from `${CLAUDE_PLUGIN_ROOT}/skills/conversion-page-audit/references/report-template.md`, with `score.py`'s `line` quoted word for word in the Conversion Score block. The header line reads `**Mode:** [Search (keyword: <keyword>) / Direct] · **Page role:** [homepage / service / landing] · **Traffic:** [cold outreach / ads / search / mixed / unknown] · **Register:** [archetype]`. On a Search page a `## Search check` block follows the score table, in the template's format, and stays outside the score; its "Headings" line reads `**Headings (whole page, footer included):** ...` because the heading counts cover the whole page, footer and navigation included, while the body uses leave them out; a Direct page has no such block. When the keyword is not confirmed, the block shows the title, the H1 and the apparent target (or says the two share no topic) and asks the user for the keyword; no placement is checked, no miss is reported, and the client version carries no Search leak (no Search leak without a confirmed keyword).
13. The client version, per `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/client-version.md`, then run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/client_check.py <client file>` and fix every FAIL. On a Search page each missed placement is one leak in the usual format (what I saw, why it costs leads, the fix, the effort), with no score and no tool names.
14. Output paths, exactly: the report `<project folder>/[C] Conversion Audit — <Page> — <YYYY-MM-DD>.md`, the client version the same name ending `— client.md`, the data `<project folder>/_audit-data/<page-slug>-<YYYY-MM-DD>/` holding `score.json`, `speed.json` and `render/`, and on a Search page `search.json`. Outside a project: wherever your project keeps audit output. In an eval run: the run's `outputs/` folder with the same names.
15. The free diagnosis carries no score; the score stays in the internal report and in paid work. To show before and after, run the same audit again after the fixes and quote both `score.py` lines. A re-score compares only within the same mode: if the page's mode changed, the report says so and treats the new audit as a new baseline.
