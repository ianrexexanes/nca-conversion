# The /cro design procedure

This is the procedure `/cro design` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as a frame's file name, goes in quotation marks. Work through the steps in order. The output is `<project folder>/_design/tokens.json` and `<project folder>/<Page> — Design Notes — <YYYY-MM-DD>.md`, with a `## Design rulings` heading in the notes, or wherever your project keeps design output.

The design starts from a checked wireframe, never from a blank canvas, so the copy and the layout are settled before any colour is chosen. A design changes how the page looks and leaves its words and its order alone.

1. Take the checked wireframe frames `/cro wireframe` produced and the approved deck. If a frame has not passed `wire_check.py`, send the user back to that step and design nothing. Read the Conversion Brief too: it holds the audience, the offer and the register that every choice below answers to.
2. Settle the style guide: the colour tokens, the type scale and the spacing scale. Take them from the client's brand files or from the live site first. When the Paper MCP is connected, read the project file's tokens with `get_tokens`, asking for `types: ["color", "fontSize"]` and `format: "css"`, which returns custom properties under `:root`. Paper's token names are the file's own, so ask the user which token is the text, background, action and action-text colour, and write their answers, with the token names, into the Design Notes. The mapping is theirs; never guess it from a name or a value. With Paper off, or with no tokens in the file, ask for the same four colours and the two type sizes directly.
3. Write `_design/tokens.json` in the format `design_check.py` reads: `{"colors": {"text", "background", "action", "action_text", ...more}, "type": {"h1_px", "body_px"}}`, each colour as `#rgb` or `#rrggbb`. Add any further colour tokens beside the required ones, and no phone type sizes, because no rule reads them.
4. Answer Hallmark's four questions from the Conversion Brief, and ask the user nothing the brief already says. The material is the brief's visual inventory and proof; the audience is its ICP and personas; the use is the one action in the deck's call to action; the tone comes from the register. Say what you inferred in a single line at the top of the reply. A fact the brief lacks stays absent, so no invented number, quote or logo goes into the design.
5. Design the page through the ladder in `${CLAUDE_PLUGIN_ROOT}/skills/design-handoff/references/design-rules.md`. That file holds the rules, their order and the form of a ruling line; this one restates none of it. Work down the ladder: Impeccable sets direction and craft, then Hallmark's Floor applies as design rules, then UI/UX Pro Max, frontend-design and Taste are consulted as inputs for style and layout. A skill that is off is skipped, and the output says so. Style the frame's HTML with the tokens as custom properties; with Paper on, draw the same design there as well.
6. Guard the conversion rules while you design. The button stays the loudest thing on the first screen, the directional cue still points at it or at the form, and the phone layout stays its own column. No design choice moves, shortens or hides a word of the deck.
7. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/design_check.py "<project folder>/_design/tokens.json"`. Fix each FAIL in the tokens, and report each WARN to the user. A token set that still fails is not handed on. Contrast is measured on the tokens, so also look at any text that sits on a photo or a gradient, where the tokens cannot see it.
8. With Hallmark and Node both on, run `node <the path doctor printed on its hallmark-lint line, the plugin's sloplint.mjs> "<styled frame html>" --render`. Each FAIL is matched to a ruling line, or the design is fixed. When doctor's hallmark-lint line says `render tier off`, run it without `--render` and write "Hallmark render checks skipped: render tier off" in the design notes. Without Hallmark, or without Node, or when the design exists only in Paper, write "Hallmark lint skipped: <reason>" in the notes and the reply; a Paper-only design waits for an HTML export before the lint can run.
9. Write every departure from a design skill as a ruling line in the form `design-rules.md` sets, naming the skill. A Direct page that uses the `prooftop` line above its H1 carries that file's standing pair of ruling lines for it, copied unchanged. The reason on every line is the conversion rule, and the departure is the user's ruling, not a waiver from the skill. Put the lines under `## Design rulings` in the Design Notes.
10. Take the blur capture. Serve the folder that holds the styled frame with `python3 -m http.server --bind 127.0.0.1 <port>` from it, in the background, with a free port. Run `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/render_check.py "http://127.0.0.1:<port>/<the file name, percent-encoded>" --out "<dir>" --blur`, then stop the server. It adds `desktop-blur.png` and `phone-blur.png`, the first screen at each width with an eight-pixel blur. Look at both and answer one question: is the button the most visible thing in the blurred first screen? If it is not, change the design, not the copy, and capture again. If the venv python does not exist, say the blur capture was skipped.
11. Hand over Hallmark's audit as one line, `/hallmark:hallmark audit <file>`, and say it is waiting: Hallmark runs that review only when the user names it, so this step never runs it.
12. Report where the tokens and the notes are, which design skills were used and which were skipped, the lint result or why it was skipped, the check's output, the answer to the blur question and the audit line. Offer the next step: the built page, which `/cro check` then reviews.
