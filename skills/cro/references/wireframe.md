# The /cro wireframe procedure

This is the procedure `/cro wireframe` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as the deck's file name, goes in quotation marks. Work through the steps in order. The output is one checked HTML frame per variant, `<project folder>/<Page> — Wireframe — <variant> — <YYYY-MM-DD>.html`, with the variant left out of the name when the deck has only one, and then the same frames drawn in Paper.

The copy is settled before a frame exists. A frame carries the deck's words and nothing else, so a layout never gets built around a line that is still being argued about.

1. Read the approved deck, the one `/cro page` wrote, and run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/deck_check.py "<deck>" --final`. If it fails, stop: name what is open, send the user back to `/cro page`, and draw nothing. A named gap in the deck becomes a hole in every frame. Read the Conversion Brief's visual inventory too, because it says which sections have a real image.
2. Build one frame per variant. The variants are the hero versions the deck carries (`<ns>.hero.a.h1`, `<ns>.hero.b.h1` and so on); ask the user which to build when there is more than one, and build exactly those. A deck with one version gets one frame and no variant in the file name. A frame never shows another variant's headline, its button label or its visual.
3. Pick a layout family for each section. When UI/UX Pro Max is on, run its layout pass for the page and take its suggestion for each section, then check it against the layout table, "Layout families by section" in `${CLAUDE_PLUGIN_ROOT}/skills/design-handoff/references/section-to-component.md`. A suggestion outside the section's row loses to the row. When it is off, use the table alone and take the first family in the row unless the section's job says otherwise: awareness decides the hero, so cold visitors get `split-media` and warm visitors get `form-split`. Say in the output which of the two was used. When Impeccable or Taste is on, take direction from them as `design-rules.md` ranks them, and name any that were off in the report.
4. Write the frame as HTML, in this format. The checker reads it, and so does the Paper route below.
   - `<main data-deck="<deck file name>" data-ns="<ns>" data-variant="<v>">`, with `data-variant` empty for a deck with one version.
   - One `<section data-section="<ns>.<section>" data-layout="<family>">` for each deck section, in the deck's order.
   - `<ns>.header.nav` is a list split on semicolons, and each label is its own link carrying the key `<ns>.header.nav` or sits inside one element that does.
   - The `prooftop` element comes before the H1 on a Direct page and after it on a Search page.
   - Every piece of visible text is a leaf element carrying `data-key="<the full deck key>"`, holding the deck's text unchanged. Write nothing visible that has no key: no placeholder words, no extra labels.
   - Every button is an `<a>` or a `<button>` carrying the key it stands for. All of them show the frame's label, which is `<ns>.cta.hook.<v>` when the deck has one for this variant and `<ns>.cta.button` when it does not, including the header button and the hero button. The doubt reducers, `<ns>.cta.fud`, sit under the hero button.
   - Keep a visual per section: each section except the header and the FAQ holds `<figure data-visual="<visual key>">`. The key is `<ns>.<section>.visual`; the hero uses `<ns>.hero.<v>.visual` when this variant has its own and `<ns>.hero.visual` when it does not. Put a real image in the figure when the brief has one for that section. Where it does not, the figure is a plain box holding the deck's description of the visual, word for word, so the box says what the picture has to show. A section whose visual line in the deck starts with `none` carries no figure.
   - The page and meta keys are not drawn. They belong to the built page, not to a wireframe.
   The design rules in `${CLAUDE_PLUGIN_ROOT}/skills/design-handoff/references/design-rules.md` apply to every frame: read it for the directional cue toward the button or the form, for the carousel rule, and for the phone layout. This file does not restate them.
5. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/wire_check.py "<frame>" --deck "<deck>" --variant <v>` for each frame, leaving `--variant` out when the deck has one version. Fix every FAIL in the frame: a changed word is put back (`PARITY`), a dropped element is restored (`MISSING_KEY`), a section gets its figure (`VISUAL`), a layout is moved into its row (`LAYOUT`), a button becomes an `<a>` or a `<button>` (`BUTTON`). The sections are put back in the deck's order (`SECTION_ORDER`). An element whose key the deck does not hold is removed, because it is copy the deck never approved (`NOT_IN_DECK`); copy that has to be added is `/cro page`'s work. Never edit the deck to quiet the checker: if the copy has to change, that is `/cro page`'s work, and the frame is rebuilt after it. Report each WARN (`EXTRA_TEXT`, text outside every key; `FOREIGN_KEY`, another variant's key or the shared slot this variant replaces; `PROOFTOP_POSITION`, `prooftop` on the wrong side of the H1) to the user. A `NOTES` WARN at this step only means the notes block is not written yet: it is written in step 8. A frame that still fails is not drawn.
6. Draw the frames in Paper when the Paper MCP is connected. Load its guide first, `get_guide` with the topic `paper-mcp-instructions`, once per session. Read the file with `get_basic_info`, and read the font list with `get_font_family_info` before the first typographic style. Make one artboard per width, 1440 for the desktop frame and 390 for the phone frame; the phone frame is its own single column, never the desktop one shrunk. Write one section per call from the checked HTML, so each write adds one visual group, and take a screenshot after each meaningful change. Where content clips, let the artboard height fit its content. When a frame is done, call `finish_working_on_nodes` on the nodes you touched. Draw the frames in the project's Paper file, and ask before creating a new file.
7. Without Paper, serve the folder that holds the frames: run `python3 -m http.server --bind 127.0.0.1 <port>` from it, in the background, with a free `<port>`. Then run `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/render_check.py "http://127.0.0.1:<port>/<the file name, percent-encoded>" --out "<dir>"` for each frame, with `<dir>` a folder for that frame's screenshots. It captures the first screen and the full page at both widths, 1440 and 390. Stop the server when the last frame is done. If the venv python does not exist, say that the screenshots were skipped and that the HTML frames are still the deliverable.
8. Write a notes block for each frame, at the end of its HTML file as a comment after `</main>`, and give it to the user in the reply: one line per section, `- <section>: <family>, because <the rule behind it>.` The rule is the section's job from `section-to-component.md`, the awareness that picked the hero, or the design rule the choice meets. A departure from a design skill is a ruling line in the form `design-rules.md` sets. Then run `wire_check.py` again on the frame with the same arguments as step 5, because the layout is checked against the notes and the notes block did not exist at step 5. Every FAIL of the second run is fixed before the frames are reported: where a `NOTES` or `LAYOUT` FAIL says a notes line and a section's layout disagree, the two are made to agree, and the check is run again.
9. Report where the frames are, which layout source was used (the layout pass or the table), which route drew them (Paper or the local screenshots), and what was skipped because a companion was off. Offer the next step: the design step takes these frames and the deck.
