# The /cro diagnose procedure

This is the procedure `/cro diagnose` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as a folder name, goes in quotation marks. The output is a buyer-path diagnosis of one site, internal first and then a client version.

The walk keeps the buyer-path order, from the visit to the sale, rather than starting with whether people want the offer, because a free diagnosis sees the traffic and the page from outside; only the owner's data answers whether people want it. Start no subagents, and use no browser tool from an MCP server: every leg runs in this conversation, one after another, and a page is rendered only by the plugin's own scripts, which block the site's analytics.

1. Before the walk, ask once, in one message, for whatever is missing: the page address and what `/cro audit` asks (the mode, the keyword on a Search page, the traffic source, the page role and the register); whether the owner takes part (answers questions, shares their analytics, may give a yes for a test lead for this test); whether the user has Search Console access for the site; and the name for the client version's `**Written by:**`. Then run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/doctor.py --data-dir ${CLAUDE_PLUGIN_DATA}` and read two of its lines: `companions`, which names claude-seo when it is missing, and `clarity-token`, which says where a Clarity token comes from and never shows it. Every leg writes into one audit data folder for the page, `<project folder>/_audit-data/<page-slug>-<YYYY-MM-DD>/`, the folder `/cro audit` uses.
2. **Traffic and search: are the right people arriving?** Find where the visitors come from: the owner's answer when the owner takes part, else the user's. Read it through `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/lead-sources.md`: what that visitor already knows, and whether the page keeps the promise the source made before the click. A source nobody can name goes in the report as a question for the owner. On a Search page, run claude-seo's `seo-page` on the page's raw HTML, never with claude-seo's render option, because claude-seo's renderer does not block the site's analytics. Add claude-seo's `seo-google` for the page's Search Console data when the user has Search Console access; it checks its own credentials first, so report the access it found, and when it finds none, that part is skipped, because no Search Console data can be read. Without claude-seo, run `search_check.py` with the command `audit.md` step 4 gives, into the audit data folder; the claude-seo part is skipped, because claude-seo is not installed, and the page leg reuses that `search.json` instead of running audit step 4 again. On a Direct page the search part is skipped, because its visitors come from the source the owner named, not from search. Never run claude-seo's `seo-audit`: it audits a whole site and hands its work to subagents. Keep the findings and leave claude-seo's own score card out of the client version.
3. **The page: do they see it is for them?** Run `/cro audit`, following `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/audit.md` through steps 1 to 12, with step 14's data paths, but not step 13: the diagnosis's client version carries the page's leaks, so the audit writes no client file of its own here. The audit's internal report stays in the audit data folder as the page leg's evidence; the diagnosis report cites it and does not copy it. Step 1's questions were asked in this procedure's step 1, so do not ask them again. When factor 1 or factor 2 scores 6 or under, read `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/positioning.md` and name the positioning gap: the part the owner cannot state, and the part of the page it should feed. Whatever the audit lists under Could not check goes into `## Skipped legs` as well, with its reason.
4. **Form and behaviour: do they act?** Run `/cro form` as `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/form.md` gives it: its steps 1 to 5, the read-only test and the two simulations, which send nothing, with each test in its own folder under the audit data folder (`read-only`, `simulated-success`, `simulated-error`) as `--out`; stop before its step 6. A page without a form: say what its action is (a booking link, a phone number) and skip the form test with that reason. Then run `/cro data` as `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/data.md` gives it, when its sources exist: a GA4 server or export, or a Clarity token (the `clarity-token` line from step 1). Otherwise skip it with its reason, naming which source is missing.
5. **Follow-up: what happens after they act?** Ask the owner how fast a lead is answered, who replies, and what the next step is that the page and the form promise. Judge the answers by `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/sales-follow-up.md`, whose rule is that a lead hears back within minutes, not days. The page cannot show the reply time, so the owner's timestamps are the evidence, and the report marks them as the owner's word. The thank-you step comes from step 4's form test (`form.md` step 5): what it says happens next, and when. A test lead goes out only with the owner's yes, given for this test, through `form.md` steps 6 and 7: `form_consent.py`, which Claude Code asks about before it sends in its default permission mode, because no rule pre-approves it; with permission prompts off, `form.md` step 7 says what to do instead. If the user declines the prompt, nothing was sent, and the report says so. Without the owner, only the thank-you step is read and the rest of the leg is skipped, because nobody can answer for the follow-up.
6. **The offer: would they buy?** Run `${CLAUDE_PLUGIN_ROOT}/skills/offer-architect/references/offer-audit-checklist.md` over the offer as the page states it, and over the owner's answers when the owner takes part, with no composite score, which is the checklist's own rule. Name the one constraint that stops the sale and rank the rest by what leaving each costs. Without the owner, the answers the checklist needs from the owner are skipped, because the owner is not taking part.
7. **Demand: do people want it?** Asked last, and only when every other leg passes and leads still do not buy. The question then is demand, which goes back to `/cro research`, as `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/research.md` gives it. A free diagnosis does not reach it, because only the owner's data answers it, and the report says so. When an earlier leg still holds a leak, this leg is skipped, because that leak comes first.
8. Say which legs were skipped and why. In the internal report's `## Skipped legs`, write one line for each skipped leg or skipped part of a leg, in the form `- <leg>: skipped, because <reason>.`, with the reason taken from the step where the skip happened. A leg is never left out silently.
9. Write the internal report, `<project folder>/Buyer-Path Diagnosis — <Site> — <YYYY-MM-DD>.md`. It opens with what was read: the pages, the owner's answers, the exports, the Search Console data, and whether a test lead was sent and with whose yes. Then one `## ` section for each leg that was walked, named `## Traffic and search`, `## The page`, `## Form and behaviour`, `## Follow-up`, `## The offer` and `## Demand`, each with its findings and the files they came from, the page leg quoting `score.py`'s `line` word for word. Then `## Skipped legs`, from step 8, and then `## Leaks in fix order`: every leak across the legs, ranked by what it costs, an earlier leg first where two cost about the same, because a visitor lost early never reaches the later legs.
10. Write the client version, `<project folder>/Buyer-Path Diagnosis — <Site> — <YYYY-MM-DD> — client.md`. It follows `${CLAUDE_PLUGIN_ROOT}/skills/cro/references/client-version.md`, and its summary holds the three costliest leaks across the legs, in the order to fix them, with no score and no factor table. A leak seen outside the page says where it was seen: the form test, the owner's own figures with their dates, or the owner's answers. The `**Method:**` line says what was read and whether a form was sent, and names no tool and no AI: when only public pages were read and nothing was sent, it is that file's own line, `Public pages only. No logins, and no form was sent.` Then run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/client_check.py <client file>` and fix every FAIL.
11. After the fixes, run the diagnosis again. The page leg's two audit data folders, the one from this run and the one from the re-run, go to `/cro compare` (`${CLAUDE_PLUGIN_ROOT}/skills/cro/references/compare.md`), and every other leg is read again from its own new evidence: the form test again, the owner's new answers and figures with their dates, and new Search Console data. A leak is marked fixed only when that new evidence shows it.
