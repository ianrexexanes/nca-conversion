# The /cro form procedure

This is the procedure `/cro form` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as a page address with a query or a folder name, goes in quotation marks. The output is one report on the form: what it asks for, what a visitor sees when it works, what a visitor sees when it fails, and what happens next.

The read-only test is the default and the first thing that runs. The simulated success and the simulated error come second and send nothing either. The consented send comes last, and it runs only with the owner's yes, given for this test. If the user did not ask for a real send, stop after step 5 and say so in the report.

1. Read-only test. Run `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/form_check.py "<page address>" --out "<folder>/read-only"`. When the page holds more than one form, add `--form "<css selector>"` to name the one to read; a read-only run without it reads them all. The script opens the page in the plugin's guarded browser with analytics blocked, reads every field, the status and error regions and the thank-you link, saves a picture of the form at desktop width and at phone width, and presses the submit control once with every field empty to see the browser's own validation messages. A route on the browser context aborts every request to the form's action address first, whatever its method, and to every submit control's own `formaction` address. The form's target is set to the same page and `window.open` returns null before the press, but a page that saved `window.open` earlier, or that clicks a `target="_blank"` link itself, can still open a popup during the press. Such a popup is under the guard's context rules (every non-GET request aborted, the blocked hosts stopped) and under the form-address route, but not under the address block the guard puts on the page it opens itself, so a GET the popup sends to a path on the site's own host is not covered. The guard aborts every other non-GET request. So no non-GET request leaves in this run at any time, and after the route is installed no request to the form's address leaves; a GET that the page's own script sends somewhere else is not covered, and neither is a GET to that address while the page loads or on the phone pass. It prints one line for each finding and writes `form.json` and `network-log.json` into the folder. A `FAIL ... SENT` line means a request left the browser; stop, report it, and do not go on to the later steps.
2. Read the findings and the fields. `FIELD_COUNT` is a WARN when the form shows more than four fields; `CAPTCHA` is a WARN when a challenge is visible; `TARGET` is a WARN for each control that is under the recommended touch size at phone width, with its size. A WARN is a question for the owner, not a failure: read `form-and-signup-audit.md` for how to judge which field is worth its cost, and treat a figure from any outside study as a signal for what to question first, never as a promise for this form. In `form.json`, read each field's label, type, `required`, `autocomplete` and `inputmode`: a field with no label, an email field that is not an email type, a phone field without a phone keyboard, or a field with no `autocomplete` value are findings to list. Open the pictures and look at them; the script reads the markup and the boxes, and a person reads the layout.
3. Simulated success. Run the same command with `--out "<folder>/simulated-success"` and `--simulate success`, and with `--form` when the page holds several forms. The script fills archetype test data, marks it as a simulation, presses submit, and answers the form's action address itself with a success reply, so the page shows its own success state. No non-GET request leaves the browser, and once the route is installed no request to the form's address does: the log marks that request as answered by the script. Read `submit.state`, `submit.status_text` and the picture `form<n>-simulate-success.png`. A form that sends to an address other than its action prints `SKIPPED ... SIMULATE` with that address; say that this form could not be simulated and give the reason.
4. Simulated error. Run it again with `--out "<folder>/simulated-error"` and `--simulate error`. The page now gets a server error for the same submission. Read what the visitor sees: whether the message says what went wrong in plain words, keeps what the visitor typed, and offers another way to reach the owner, such as an email address or a phone number. A page that shows nothing, or shows a success message after a failure, is a finding.
5. Read the thank-you step, which is where what happens next is told. Take the page address from the `thank_you` entry in `<folder>/simulated-success/form.json`: the new address when the page navigated, else the status text it showed in place. For a form with a redirect field the read-only run lists the thank-you link; open it with `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/render_check.py "<thank-you address>" --out "<folder>"` and read its text. Say in the report whether it thanks the visitor and stops, or tells them what happens next, who replies, and when the reply comes. A thank-you page that only closes the loop is a finding: the visitor has no step to imagine and no time to wait for. What the owner's team really does after a send cannot be seen from the page, so a promised reply time is a claim to check against the inbox, and the report says so.
6. The consented send comes last, and only with the owner's yes, given for this test. Ask the owner first, in plain words: that one real submission will go to the form's own address, that their team will see it as a lead, and what it will say. Take their name, today's date and an address they read, and write the date as year, month and day with hyphens. A yes for another test, another form or an earlier day does not count; the date must be today's. A second run is a second lead and needs its own yes.
7. The consented send. The command is `${CLAUDE_PLUGIN_DATA}/venv/bin/python ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/form_consent.py "<page address>" --out "<folder>/consent" --owner "<owner's name>" --date <today as YYYY-MM-DD> --email <owner's address>`, with `--form` when the page holds several forms. Always print the exact command with every value it will send, both folders written out in full, and ask the user for the owner's yes to it in the chat, whatever the permission mode. On that yes the user runs the command in a terminal of their own; do not run it yourself. Unless the form sends to the machine's own loopback address, the script prints the host the form sends to and sends only when a person types that host back at the terminal; a run with no terminal prints `SKIPPED ... SEND` with exit 3 and sends nothing. When the user says it has run, read `<folder>/consent/form.json` for the result. If the user declines, nothing was sent, and the report says so. What the script does: it exits with 2 before a browser opens when the owner's name is empty, the date is not today's or the address is not an address. It fills the form, then opens the guard to one non-GET request, to the form's own host, for the press alone, so nothing the page sends while it loads can use the send. It refuses a form that submits by GET, because the guard cannot count or limit a GET: `SKIPPED ... SEND`, exit 3, nothing sent. It prints `SKIPPED ... SEND` too when the form sends to a host the guard blocks or to another host. The one send goes only to a request whose body carries the address given in `--email`. When no request to the form's host carries it, such as a form with no email field or one that sends the address in another shape, it prints `SKIPPED ... SEND` with exit 3 and sends nothing. When the form's own validation refuses the fill, the script prints `not sent: the fill does not satisfy <field> (<message>)`; tell the user the field and the message and that nothing was sent. When the one consented request went to a different address than the form's action, most likely the page's script sending the form there, it prints `WARN ... SEND` with exit 0: check that the test lead arrived before any rerun. It reports a `FAIL ... SEND` and exit 1 when the request that took the send was not the form's own and the form's own request was aborted, when a request reached the form's address besides the send, or when a second non-GET request completed because the form's address answered with a redirect that keeps the method: the guard cannot see the hop, so it can only report it afterwards, and the report must say that a second submission may have reached another address.
8. Report. Give the form's fields as a table (label, type, required, autocomplete), then the WARN lines with the owner's question for each, then the simulated success and the simulated error as what a visitor sees, then the thank-you step: what it says happens next and when the reply comes, and whether that promise was checked. If step 7 ran, add the time from the press to the thank-you state from `submit.time_ms`, and ask the owner to say when the reply arrives so the report can state the real wait. Name what was not checked: the form's behaviour when the network is slow or the script is switched off is the site owner's own test and not part of this procedure. Hand the findings that need a fix to `/cro audit` or to the site's builder, and keep every claim tied to this form, not to a study of other forms.
