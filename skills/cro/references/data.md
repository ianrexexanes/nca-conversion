# The /cro data procedure

This is the procedure `/cro data` follows. It writes the plugin's folder as `${CLAUDE_PLUGIN_ROOT}` and its data folder as `${CLAUDE_PLUGIN_DATA}`. The shell sets neither one, so put the full paths the `cro` skill gave you in their place in every command you run and every file you read. Any argument that can hold a space, such as a folder name, goes in quotation marks. The output is one block of behaviour figures for the audit and the brief, each with its source and its dates.

Two sources, and either can be missing. The block says which one was used and which was not.

1. Read GA4. When a GA4 MCP server is connected to Claude Code, call its report tool (name it by what it does, since a server's tool names differ). Ask for the last 28 days: the landing page, form starts, and lead or thank-you page views, by device and by source and medium. Without such a server, ask the user for a GA4 export of the same report, and say in the block that the export was the source. Keep the date range and the property the figures came from.
2. Check the Clarity token before any call. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/doctor.py --data-dir ${CLAUDE_PLUGIN_DATA}` and read the `clarity-token` line. It shows where the token comes from, never the token. Never ask for the token in the chat: when it is missing, point to `setup.md` (the Clarity token section) and go on with GA4 alone.
3. Read Clarity. Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/cro/scripts/clarity_export.py --project <name> --days 3 --dimension URL --dimension Device --out "<audit data folder>/clarity.json" --data-dir ${CLAUDE_PLUGIN_DATA}`. One call with `URL` and `Device` covers most pages. It writes `clarity.json` and prints one line. For a second project's token, add `--token-file "<path>"`. The API allows ten requests per project per day and the script keeps a local count and refuses the eleventh (exit 4), so do not repeat a call to see if it changes. The quota's reset time is UNVERIFIED: no documentation states it, so a 429 from the API is the authority, and the script reports it as the daily limit whatever the local count says. Exit 3 names the HTTP status: 401 means the token is missing, invalid or expired, 403 that it is not authorised for the project, 400 that the parameters were refused. Report the reason and go on without Clarity.
4. Read `clarity.json`. `metrics` holds each metric's rows as Clarity sent them. When `truncated` is true, a metric reached 1,000 rows, the API sends no more, and the block says so. When `reason` is set, `metrics` is empty and no Clarity figure exists. Pick the rows for the page being audited by its `URL` and `Device`.
5. Say what each figure suggests, and keep it to a signal for what to look at, never proof of a cause:
   - Rage clicks and dead clicks on a control: factor 9 (design that sells), where something looks clickable and is not, or does not respond. Name the element.
   - Quick-backs from an ad or a search result: factor 2's message match. The visitor left for the page they came from, so the promise they clicked and the page's first view did not line up.
   - Scroll depth: where the page loses people. Compare the share who reached the form or the offer with the share who reached the page's end.
   - Form starts against leads in GA4: factor 8 (the form and what happens after it). Many starts and few leads point at the form, its fields or the step after it.
6. Write the block for the audit and the brief. Each figure carries its source (GA4 or Clarity), its dates (the 28 days, or the 72 hours Clarity covers, in UTC) and its device and source cut. A figure the data does not hold is reported as missing, never estimated or invented. Say which source was skipped and why. Do not add a conversion rate that neither source gave.
